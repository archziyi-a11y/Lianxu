# 工作流试验结果 · 2026-10-28

结论：保留 Maestro + ADB + 本地证据整理器。它改善了复现、版本核对与动效定位，且帮助发现并修复一个真实转场缺陷；本轮没有证明总耗时显著下降，也没有证明可以取消人工式视觉审阅。

## 实际完成

- 安装官方 Maestro 2.11.0，SHA-256 校验通过。没有安装其他移动控制插件，也没有使用云测试或云录屏。
- 独立 evidence APK 与内存样本复用正式界面，使用真实 Android 动画时钟。已有业务数据库、密钥、原交付 APK 不被测试样本覆盖。
- 同一场景分别通过 Maestro YAML 和 ADB 实际操作：卧推、接续上次两卡长按→文字输入→统一发送→回复可见。
- 结果核对：一条完成轮次、两条原文完整、历史训练仍为六条。离线 AgentClient 仅返回固定验证回复。
- Maestro MCP 已通过 stdio 初始化、工具发现、设备发现、`inspect_screen` 与 `run` 可见性断言。未修改全局 Codex MCP 配置；当前聊天不会因此自动获得新的原生工具。
- 自动保存唯一运行目录、APK/源文件/流程摘要、动作与业务事件、数据库结果、完整录屏和关键图；生成事件附近短片、连续帧与本地集中审阅页。

## 发现、修复与证据

1. 启动命令成功不等于样本就绪。初期两次启动留下桌面或旧实例，本轮编号的 ready 检查拒绝继续；修为清理旧 Activity 任务并同步等待启动。
2. 最终回复可见不等于转场正确。修复前，旧卡片先入场，新回复随后插入。新增边界回归实际失败：处理状态结束时首卡是“能量目标”，应为“本轮建议”。
3. 修复为结束处理前发布最新草稿与解析结果，并拒绝迟到的旧版本；取消过时解析，避免重复解析已发布版本。最终 ADB、Maestro 连续帧均显示新回复随整张看板从下方进入，待发送栏没有闪回。
4. 收集器早期截取发送连续帧过晚，改为提前 0.6 秒，保留动作起点。时间锚点仍是近似值，不能据此断言毫秒级性能。
5. 两次后续 Maestro 运行超过原 20 秒回复限制。主机当时可用内存不足 1GB；停止构建守护进程后约 3.5GB，之后两种驱动均在原时限内通过。这个前后观察支持环境负载是因素，但没有对资源压力与解析优化做独立消融，不能量化各自贡献。

[集中审阅页](workflow-runs/review-accepted-20261028.html)：第一项是修复前的问题证据，后两项是最终同包对照。保留完整录屏；短片约十余秒，支持半速与逐帧跳转。
